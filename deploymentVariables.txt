# Deployment variables and secrets

GitHub secrets are write-only. This inventory records names, scope, sources,
and safe generation steps without exposing secret contents. The application
workflow deploys merged `develop` changes to test and merged `release` changes
to production. Database name, backend port, TLS mode, and Java memory settings
are selected by the workflow rather than configured as GitHub variables.

See the [deployment flow diagram](.github/modernize/assessment/engines/facts/architecture-diagram.md)
and the [deployment runbook](deployment/README.md) for the end-to-end process.
For the ordered setup checklist, see [deployment-steps.txt](deployment-steps.txt).

The deployment importer accepts the exact names shown in
[`deployment/aws/github-actions.env.example`](deployment/aws/github-actions.env.example).
Its input file is a local credential file, not a workflow artifact; keep it
ignored and set permissions to `600`. `MYSQL_DATABASE`, `SERVER_PORT`,
`MYSQL_SSL_MODE`, `MYSQL_ALLOW_PUBLIC_KEY_RETRIEVAL`, `SPRING_PROFILES_ACTIVE`,
`SERVER_ADDRESS`, and development seeding are fixed by the workflow/deploy
script and are not user-configurable deployment variables.

**Production database decision required:** the current repository-level
`MYSQL_HOST` points to RDS, while the production Terraform example provisions a
Lightsail MySQL database. The application deployment workflow does not migrate
data between them, and the backend deploy script creates an application DB
account only for the test host. Keep the current production DB settings until
the target database, schema, app user, grants, credentials, data migration, and
rollback plan are explicitly agreed and verified.

## Terraform infrastructure inputs

The root `deployment/terraform` stack takes its non-secret settings from
`env/test.tfvars` or `env/prod.tfvars`. Copy the matching `.example` file; both
real `.tfvars` files are ignored by Git.

| Input | Required / default | Where to get or how to choose it |
|---|---|---|
| `environment` | Required: `test` or `prod` | Already set in each example file; the wrapper also selects a matching Terraform workspace. |
| `aws_region` | Defaults to `us-east-2` | Choose an AWS region with the needed Lightsail and EC2 resources; keep both environments in the intended region. |
| `availability_zone` | Optional; defaults to the first available zone | Leave unset unless you have a placement requirement. List zones with `aws ec2 describe-availability-zones --region us-east-2 --query 'AvailabilityZones[?State==`available`].ZoneName' --output table`. |
| `application_name` | Defaults to `bingo` | Keep the default unless intentionally creating a separate stack name. |
| `instance_bundle_id` | Required for production; example `medium_3_0` | Select a Lightsail Ubuntu instance bundle in the AWS console, or list bundle IDs with `aws lightsail get-bundles --region us-east-2 --query 'bundles[].bundleId' --output table`. |
| `database_bundle_id` | Required for production; example `medium_2_0` | Select a Lightsail MySQL bundle in the AWS console or inspect the Lightsail bundle list. |
| `database_admin_username` | Defaults to `bingo_db_admin` | Keep the dedicated database admin name unless the database policy requires another. |
| `database_admin_password` | Required for production; never put it in tfvars | Generate a unique password and export it as `TF_VAR_database_admin_password` in the same shell used for plan/apply. Terraform marks it sensitive in output, but protect Terraform state as secret data. |
| `ssh_allowed_cidrs` | Required operationally for SSH access | Use a known, trusted `/32` operator address or a stable self-hosted runner range. `curl -4 https://checkip.amazonaws.com` shows the current client IPv4; do not assume GitHub-hosted runner egress is stable and never use `0.0.0.0/0`. |
| `ssh_public_key` | Required for the test EC2 key pair | Use the public half of the dedicated deploy key. Never put its private half in tfvars. Generate the pair with `ssh-keygen -t ed25519 -f ~/.ssh/bingo-test-deploy -C bingo-test-deploy`. |
| `test_instance_type` | Test only; defaults to `t3.micro` | Change only after checking AWS availability and cost. |
| `test_root_volume_size_gb` | Test only; defaults to `20`, allowed range `8` to `30` | Change only after reviewing storage cost and bootstrap requirements. |
| `test_vpc_cidr`, `test_subnet_cidr` | Test only; defaults to `10.77.0.0/16` and `10.77.1.0/24` | Keep these non-overlapping with connected VPCs; adjust only with a network plan. |
| `test_site_domain`, `test_admin_domain` | Test only; default `test.bakaroo.com` and `admin.test.bakaroo.com` | The names must be distinct names under `bakaroo.com`, outside the production HSTS subtree. |
| `test_api_domain` | Test only; fixed to `api.test.bakaroo.com` | Do not change; the mobile HTTP exception is locked to this host. |
| `route53_zone_id` | Optional; default empty | Set a public Route 53 hosted-zone ID to use Route 53. Leave empty to sync the GoDaddy `bakaroo.com` A records; then export `GODADDY_PAT` for test apply. |

## Optional existing-test-database schema inputs

This separate Terraform root creates the `bingotest` schema on an existing
test MySQL server. The normal EC2 test environment instead uses MySQL installed
locally by its bootstrap, so these inputs are not needed for that deployment.

| Input | Required / default | Where to get or how to set it |
|---|---|---|
| `environment` | Required; must be `test` | Keep `test`; this root rejects production. |
| `mysql_endpoint` | Required | Existing test MySQL endpoint and port, for example `db.example.amazonaws.com:3306`; it must be reachable over TLS from the Terraform runner. |
| `mysql_admin_username` | Required | Use an administrator limited to provisioning the test schema; set in the ignored `test.tfvars`. |
| `mysql_admin_password` | Required secret | Supply as `TF_VAR_mysql_admin_password` in the same shell; do not place it in `test.tfvars`. |

```zsh
cd deployment/terraform/test-database
cp test.tfvars.example test.tfvars
read -s 'TF_VAR_mysql_admin_password?Existing test MySQL admin password: '
export TF_VAR_mysql_admin_password
./provision.sh plan
./provision.sh apply
unset TF_VAR_mysql_admin_password
```

Apply and destroy ask for a typed confirmation; review the plan before
confirming. See the [test-database instructions](deployment/terraform/README.md#existing-aws-mysql-test-schema).

## Handy setup and deployment commands

Run Terraform commands from the Terraform root. The example CIDRs and public
key in `env/test.tfvars.example` are placeholders and must be replaced.

```bash
aws sts get-caller-identity
cd deployment/terraform
cp env/test.tfvars.example env/test.tfvars
cp env/prod.tfvars.example env/prod.tfvars
```

In macOS `zsh`, supply the production database admin password without echo or
shell-history exposure. Keep it set for both the production plan and apply:

```zsh
read -s 'TF_VAR_database_admin_password?Lightsail database admin password: '
export TF_VAR_database_admin_password
./provision.sh prod plan
# Review the full plan before proceeding.
./provision.sh prod apply
unset TF_VAR_database_admin_password
```

For a GoDaddy-managed test apply, enter the token only in the current shell:

```zsh
read -s 'GODADDY_PAT?GoDaddy PAT: '
export GODADDY_PAT
./provision.sh test apply
unset GODADDY_PAT
```

Retrieve outputs after applying; Terraform workspaces are separate:

```bash
terraform workspace select test
terraform output -raw web_static_ip
terraform output -raw test_ssh_user
terraform output -raw test_api_base_url
terraform output -raw test_admin_url
terraform output -raw test_site_url

terraform workspace select prod
terraform output -raw web_static_ip
terraform output -raw database_endpoint
```

Use the outputs to configure `DEPLOY_HOST`, `DEPLOY_USER`, `MYSQL_HOST`, and
the public URL variables in the corresponding GitHub Environment. `GODADDY_PAT`
is not required for plan or destroy; test DNS records are intentionally kept
when the infrastructure is destroyed.

From the repository root, create protected GitHub Environments in Repository
Settings before running deployments. The importer accepts the tracked example
names; make local files with restrictive permissions and never commit them:

```bash
umask 077
cp deployment/aws/github-actions.env.example deployment/aws/github-actions-test.env
cp deployment/aws/github-actions.env.example deployment/aws/github-actions-prod.env
chmod 600 deployment/aws/github-actions-test.env deployment/aws/github-actions-prod.env
GH_ENVIRONMENT=test bash deployment/aws/bootstrap-github-actions-config.sh deployment/aws/github-actions-test.env
GH_ENVIRONMENT=production bash deployment/aws/bootstrap-github-actions-config.sh deployment/aws/github-actions-prod.env
```

Before deploying, inspect repository variable values and secret names without
trying to read secret contents:

```bash
gh api repos/equar/bingo-platform/environments --jq '.environments[].name'
gh variable list --repo equar/bingo-platform
gh secret list --repo equar/bingo-platform
```

## Setup commands

Create separate unencrypted SSH key pairs for the test and production
environments. Put the test public key in `env/test.tfvars` and authorize the
production public key on the production host. Only the Base64 private key goes
in the matching GitHub Environment secret:

```bash
ssh-keygen -t ed25519 -N '' -f ~/.ssh/bingo-test-deploy -C bingo-test-deploy
ssh-keygen -y -f ~/.ssh/bingo-test-deploy
base64 -i ~/.ssh/bingo-test-deploy | tr -d '\n' | gh secret set DEPLOY_SSH_KEY_B64 --repo equar/bingo-platform --env test

ssh-keygen -t ed25519 -N '' -f ~/.ssh/bingo-prod-deploy -C bingo-prod-deploy
base64 -i ~/.ssh/bingo-prod-deploy | tr -d '\n' | gh secret set DEPLOY_SSH_KEY_B64 --repo equar/bingo-platform --env production
```

Run `ssh-keygen -y` to display the test public key and copy it to
`ssh_public_key` in `env/test.tfvars`. Confirm the production public key is
authorized on the host. Configure GitHub Environments before setting their
secrets.

Generate independent values per environment. These commands pipe directly into
GitHub; the encryption-key copy in your home directory is mode `600` because
of `umask 077`. Store that backup in an approved password manager before
removing the local copy. Never regenerate an encryption key for data already
encrypted with it.

```bash
umask 077
openssl rand -base64 32 | tr -d '\n' | tee "$HOME/.bingo-float-key-test" | gh secret set BINGO_FLOAT_BANK_ENCRYPTION_KEY --repo equar/bingo-platform --env test
openssl rand -hex 32 | tr -d '\n' | gh secret set JWT_SECRET --repo equar/bingo-platform --env test
openssl rand -hex 32 | tr -d '\n' | gh secret set MYSQL_PASSWORD --repo equar/bingo-platform --env test

openssl rand -base64 32 | tr -d '\n' | tee "$HOME/.bingo-float-key-production" | gh secret set BINGO_FLOAT_BANK_ENCRYPTION_KEY --repo equar/bingo-platform --env production
openssl rand -hex 32 | tr -d '\n' | gh secret set JWT_SECRET --repo equar/bingo-platform --env production
openssl rand -hex 32 | tr -d '\n' | tee "$HOME/.bingo-mysql-password-production" | gh secret set MYSQL_PASSWORD --repo equar/bingo-platform --env production
```

`MYSQL_PASSWORD` must match the selected database application account. For a
new production account, coordinate creating that account and setting its
password from the protected local file before deploying; the current
production database migration is not automated.

Use the environment importer after creating both environments:

```bash
GH_ENVIRONMENT=test bash deployment/aws/bootstrap-github-actions-config.sh deployment/aws/github-actions-test.env
GH_ENVIRONMENT=production bash deployment/aws/bootstrap-github-actions-config.sh deployment/aws/github-actions-prod.env
```
