# Module 04D-5B — Proposed Nonfinancial Claim E2E Matrix

This matrix is for execution only after Product/Security approval, DBA grant correction, fixture-runner implementation, and successful runtime guards. It was not executed in Module 04D-5B.

Every run begins with a new run UUID and a read-only baseline scoped to its synthetic player, room, session, and ticket. Capture `users`, `bingo_rooms`, `bingo_sessions`, `bingo_tickets`, `bingo_draw_events`, `bingo_win_claims`, `audit_log_entries`, `wallets`, `wallet_transactions`, `agent_float_transactions`, `commission_accruals`, `bingo_prize_entitlements`, and any settlement/journal tables present in the approved schema. Reconcile only by run UUID and linked entity IDs, never by reused numeric ID alone.

## Expected fixture records

The synthetic player is created through the ordinary registration lifecycle and selected from the dedicated allowlist. The fixture runner creates a labeled room/session, generated ticket(s), and fixture provenance/audit. Draw rows are created only by the ordinary server-selected draw service and carry its normal audit record. The claim service alone creates claims. No fixture code creates entitlements, payment/deposit records, wallet debits, agent float transactions, commissions, or settlement entries.

For valid/invalid/duplicate/concurrent/cancelled scenarios, capture returned operation IDs, HTTP status/domain code, player/ticket/session IDs, session state, draw sequence, claim IDs/status, audit IDs/action/target, and run UUID. Keep credentials, PINs, JWTs, approval capability and payment details out of screenshots and evidence.
