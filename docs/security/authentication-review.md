# Admin and Player authentication review

## Current controls

- REST is configured statelessly. Protected routes require an authenticated principal; Admin and Agent URL spaces have role matchers, and Admin routes further distinguish ADMIN from SUPPORT. Controllers/services also apply operation and resource authorization. The JWT filter reloads the user on each REST request, validates signature, expiry, user ID, and current `securityTokenVersion`, and rejects inactive/locked/suspended accounts. Token version changes revoke all existing tokens for that account.
- Player JWTs include a session ID (`sid`). Login locks the user row and rejects an unexpired active Player session unless the user explicitly chooses the replace-session flow. The request filter checks `sid` on every REST request. Logout increments token version and clears the active Player session when the presented `sid` is current; clients clear local credentials even when the remote logout call fails.
- Admin stores access tokens in tab-scoped `sessionStorage`, not `localStorage`; its API client clears only the token that received a current-session 401, not on 403 or a stale request's 401. The Nginx Admin policy includes a same-origin script CSP without `unsafe-inline`/`unsafe-eval`, frame denial, and HSTS. A source scan found no `dangerouslySetInnerHTML`, `innerHTML`, `document.write`, or eval-based sinks. React escapes ordinary interpolated text. `sessionStorage` remains readable by same-origin JavaScript, so a successful XSS could still steal the bearer token; CSP and safe rendering lower that risk but do not make JavaScript storage equivalent to HttpOnly cookies.
- Player stores the access token, expiry, and profile using `flutter_secure_storage`; it does not store a refresh token. Client-side expiry clears local state. API 401, suspension, and active-game REST failures clear credentials and stop the live socket. Reconnection rereads the current access token and requires a valid session. The server authenticates STOMP CONNECT and checks token version and Player `sid` there; subscriptions are access-checked at subscribe time.

## Existing regression coverage reviewed

`AuthSecurityIntegrationTest` exercises missing, malformed, wrong-signature, expired, and tampered JWT rejection; reuse of a token after logout; explicit one-session-at-a-time behavior; replacing a session and rejecting the old token; role boundaries; and suspension/revocation. `JwtServiceConfigurationTest` verifies token-version invalidation. Player `live_game_controller_reconnect_test.dart` verifies an expired access token ends a live-game connection rather than reconnecting with it. `auth_session_controller_test.dart` verifies local logout cleanup after server logout failure. This review added an Admin malformed-session-storage test.

Bearer access tokens are reusable credentials by design until expiry/revocation. There is no per-request single-use or stolen-token detector. Logout, version changes, and session replacement invalidate reuse after the server processes them; a copied token can be replayed before that point. No server can reliably distinguish a stolen bearer from its legitimate holder without a changed credential/session protocol or stronger device binding.

## Active-game session expiry and proposed refresh design

Today a Player session ends when the access JWT expires. REST polling/requests receive 401, the app clears secure storage and disconnects; it does not silently extend the session. This is safe and bounded but can interrupt a long game. Keep this behavior until a refresh contract and duration policy are approved.

If seamless reconnect is approved, use an opaque, high-entropy refresh secret, store only its hash server-side, and keep refresh-token families bound to the existing Player session. Rotate the refresh token atomically on every use. A second use of a consumed token marks reuse: revoke the family and active session, increment token version, and require fresh sign-in. Revoke on logout, session replacement, PIN/password reset, suspension, and account disablement. Enforce both idle and absolute expiry. Never create a refresh token for Admin from the shared mobile contract by accident.

On the Player, keep refresh material only in platform secure storage. At access expiry, a single-flight refresh may be attempted once for REST and WebSocket reconnect; install the new access/refresh pair only after the server rotation succeeds. A failed refresh, reuse response, or revoked/replaced session clears credentials and stops reconnect attempts. Reconnect STOMP with the new access JWT, then resubscribe and REST-replay missed game events. Do not persist an opt-in/longer session by default without a separately approved remember-session policy.

The refresh-token contract requires approval for: access and refresh lifetimes; whether a player may have multiple device sessions (currently exactly one); family-wide versus per-device revocation; concurrent refresh grace behavior; persistent-login consent; logout while offline; schema/audit retention; rollout of mobile clients; and the Admin browser strategy. Admin bearer storage can only be made HttpOnly by changing the web authentication boundary (for example, an Admin BFF or Admin-only secure cookie endpoint), with CSRF and origin defenses. A cookie or refresh endpoint is a token-contract change and is not introduced here.

## WebSocket revocation caveat

The WebSocket JWT is checked at STOMP CONNECT and resource access at SUBSCRIBE. An already-established subscription is not actively torn down merely because a JWT later expires or its token version changes; the Player's polling path detects ordinary expiry/revocation and disconnects locally, but server-side immediate revocation of an idle established socket is not provided. If immediate socket revocation is required, approve a connection registry/revocation event design or bounded connection lifetime and test its cluster behavior.
